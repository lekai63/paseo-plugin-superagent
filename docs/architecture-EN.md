# Architecture and design

[← Back to README](../README.md) · [简体中文](architecture.md)

## Feature overview

A Router/Worker two-tier orchestration plugin for Paseo. Following the architecture of the *Super-agent design exploration* article, it implements an event-driven super-agent orchestration layer on top of Paseo primitives, **without depending on the DeepSeek Harness**:

- **The Router evaluates per thread.** Each evaluation sends new triggers, ticket state, saved memory, and a bounded history to an independent inference API. The model returns a JSON verdict and may call the read-only `superagent_list/read/search` functions.
- **Worker agents** execute tickets in Paseo. Worktree isolation gives each ticket its own workspace. Shared isolation reuses a workspace by directory and profile. The Tasks sidebar links tickets to their Workers.
- **Worker profiles**: besides the default Worker you can configure named profiles (different models / purposes), and each profile can have its own working directory so that its Workers work in another repository or directory;
- **Direct delivery for subscriptions (fan-out, many-to-many)**: when a thread has active subscribed Workers, later events bypass the Router programmatically and go straight to **all** subscribed Workers (zero LLM calls); only when no session is available are they handed to the Router for evaluation. The Router's `subscribe` action lets a Worker that is already busy in another thread **also follow** the current thread (one Worker subscribed to several threads). Followed messages carry a `[thread …]` prefix, and reports flow back to every thread the Worker subscribes to. A Worker can unsubscribe with `superagent_unsubscribe` (pass `threadId` to leave just one thread) and hand a misrouted message back to the Router with `superagent_handback`;
- **Semantic slow path**: unmentioned group messages overheard in observe mode (context-only) are never delivered directly to a Worker; they always go to the Router, which decides (ignored by default, steer when related to a task, act only when the proactive policy allows);
- **Permission and question flow-back**: a Worker's permission requests, plan confirmations and structured questions are persisted immediately. Permission requests (every kind except `question`) need a person: the engine itself posts each one, quoted from the provider with a short approval code derived from the ticket and request IDs, to the original chat or delegating session, and the Router is not asked. Only `/approve <code>` or `/deny <code> [reason]` from a human source (the chat page, the `/superagent` slash command, or an allowlisted IM sender in the chat where the request was announced, addressing the bot), or an answer in the Worker's own session, resolves it; the engine executes the command without a model call and allows that one request once. The Router may decline a permission request but never approve one: the engine refuses an `allow` from the Router for such a request, both when planning the verdict and when replaying a persisted action, and posts the request with its code instead. Structured questions go to the Router, which answers with `respond` from established context or asks the person in the original chat. While a request is unresolved, later messages in the thread go to the Router first, are not broadcast to Workers, and do not implicitly clear the request through an ordinary steer. Requests are deduplicated by ID and reconciled programmatically after a reload; run-timeout handling is paused while waiting for input, and completion is observed again after the response;
- **Quotes belong to threads + adjacent messages inlined**: when an IM message quotes (replies to) a known trigger or Router reply (message ids recorded from channel receipts), it joins the thread of the quoted message and the quoted content is inlined for the Router/Worker. An evaluation also carries the most recent 5 unmentioned group messages the Router has not seen before this batch (traced as filtered by the admission layer, with a rolling retention of 30);
- **Speculative execution** (optional, off by default): following the proactive policy written in the Router rules, the Router dispatches `speculative` Workers in the background to quietly try things nobody explicitly raised (they do not subscribe to the thread; at most 2 at a time). A report whose first line is `DISCARD:` is silently dropped by the engine and the Worker is reclaimed; only `DELIVER:` is handed to the Router for a short retelling;
- **Cross-thread command**: find threads with `superagent_search` / `superagent_list`, read details with `superagent_read`, then steer/cancel/retry. Other threads' state is never injected into the current conversation automatically;
- **Batching**: triggers within the same batch window are merged into one Router LLM call. Once armed, the window is not reset by later messages (bounded merging: a continuous message stream cannot postpone evaluation indefinitely);
- **Watchdog (two layers).** The programmatic check runs every 15 seconds to recover missed completions, timeouts, queued evaluations, and pending actions. The optional LLM patrol supplies an activity digest to the inference API and rechecks live targets before applying the verdict.
- **Inference boundary.** The Router and LLM watchdog receive explicit context and may request read-only views of orchestration records. Workspace tools and Worker actions remain in Paseo. Inference context can include user and IM messages, Worker reports, and paths.
- **IM triggers**: Feishu (official long-lived connection), QQ (OneBot 11 / NapCat), DingTalk, WeCom and WeChat (Tencent's official ClawBot / iLink, QR-code login) receive instructions, and the Router's reply goes back to the original chat. The plugin connects as soon as it starts; messages that arrive before the engine starts (the first hook/RPC) are persisted first, and direct delivery or evaluation is made up after startup.

## Architecture diagram

```
Manual dispatch (app UI / /superagent command)
Agent delegation (superagent_dispatch injected via MCP) ──► Trigger
Worker report (flows back automatically on completion)       │
Worker hand-back (superagent_handback, misrouted message)    │
                                                             ▼
                       fast-path (length truncation / thread assignment)
                                             │
              ┌──────────────────────────────┴───────────────┐
              ▼ no usable subscription / context-only overheard  ▼ has subscriptions (incl. Workers following this thread)
        batch window accumulates → serial Router evaluation   direct delivery to all subscribed Workers (steer, zero LLM)
        (dispatch[speculative] / steer / cancel /              │ not theirs to handle: handback returns it to the Router
         retry / subscribe / reply / ignore / stop)            ▼ no longer receiving: unsubscribe
        ▲ during evaluation: recall full text by ID /   Ticket → worktree workspace → Worker agent
        │ search records / cross-thread tickets                │ completes
        │ (superagent_read / list / search)                    ▼
        │ dispatch
        └──────────────► Ticket → worktree workspace ──► report capture → report Trigger flows back → Router evaluates again

The target of steer/cancel/retry/subscribe can also be a ticket listed under "other active threads" (cross-thread command; the decision is recorded in this thread)
LLM watchdog (independent inference, timed) ── patrol digest ──► nudge/interrupt/cancel/retry/reeval/escalate (escalations tell a person through the Router)
```

State (`$PASEO_HOME/plugin-data/superagent/state.json`, written atomically): `threads / triggers / tickets / decisions / pendingActions` plus a kv store. A Ticket's `pendingRequests` keeps pending requests along with question options. Every side effect (creating an agent, sending a message) happens after the state is persisted. The side-effect actions of a decision (steer/respond/cancel/retry/stop) are first filed as `pendingActions` records and removed once they succeed; the watchdog replays them in order after a crash and retries failures (with a retry limit; once exhausted, the failure flows back as a trigger for the Router to decide again). `respond` is bound to the Worker session and request ID, so a repeated execution cannot answer another request by mistake and does not widen the persistent authorization.

## Mapping to the article's five modules

| Module | Implementation |
|---|---|
| Two-tier architecture | The Router calls an independent API and returns a verdict. Each ticket has a Paseo Worker, linked through `superagent.ticket` and ticket state. Cross-thread actions can recall target records first. |
| Event-driven | Three trigger sources (manual / agent tool / Worker report) plus the IM channels; programmatic fast-path filtering (beyond the allowlist, unmentioned group messages are traced as filtered; in observe mode they become context candidates and always go through the Router's semantic judgment, never direct delivery to a Worker). IM threads are split by channel, bot account, chat and Beijing-time date: a same-day quote continues the current thread, while a cross-day quote only brings context and does not reopen the old thread. Batch-window merged evaluation (bounded window, not reset by later messages, merged per thread); subscription fan-out with direct delivery, many-to-many (the Router's `subscribe` makes a Worker follow other threads, and reports flow back to every subscribed thread). Inline: the quoted message and the most recent 5 unmentioned adjacent group messages are inlined. Speculative execution (optional): `speculative` dispatch, DELIVER/DISCARD delivers or silently drops, concurrency limit 2. Each evaluation carries the new triggers, ticket state, and bounded context. Chain of Recall: triggers, tickets, threads and decisions in the prompt all carry IDs, and history stubs keep their IDs too; the Router uses `superagent_read` to recover the complete untruncated record by ID (a thread recall inlines the IDs of the latest 10 messages and 5 decisions and the tickets of other threads that follow it; a ticket recall inlines the followed threads and the latest 3 messages of the Worker session, expanding hop by hop along references), `superagent_list` for an overview of active threads (the latest 10), and `superagent_search` to search all records by keyword. When a Worker report flows back with truncated text, it carries a ticket recall pointer, and the first line of a report is required to be a self-contained conclusion sentence that includes key entities (path/ID/command) (stubs and search both take the beginning). Built-in memory discipline: a promise that spans turns must land in a ticket or reply, and when the target of a stop or cross-thread decision is unclear, run `superagent_list` first to reconcile. It does not repeat the user's first-line title or the body of a Ticket report; only on the first recovery of a thread are up to 8 history stubs added |
| Human-facing interaction | The Paseo app is the channel: push, attention, permission flow. Delegate from any agent session with `/superagent` or the `superagent_dispatch` tool; the Router's reply returns to the original delegating session; a person can take over a Worker session at any time. Multi-channel output style: evaluation prompts for IM-sourced threads carry a channel-style section (keep replies short; for long content dispatch a Worker and relay a summary and the output location), and over-long replies are still split automatically by paragraph when posted back. Self-healing for misrouted direct delivery: a Worker calls `superagent_handback` to return a message that is not its own to the Router for re-routing (inheriting the original IM/agent reply target), and `superagent_unsubscribe` stops further direct delivery |
| Separation of storage/compute and environment | That is the Paseo daemon itself: the daemon runs on your machine, clients (relay E2EE) can be anywhere, and the execution environment stays where it is. Persisted state (state.json) plus self-recovery after restart is the single-machine form of "separating compute from state"; stateless cloud compute and on-device daemons are not done because of the host's form (see [Design trade-offs and limitations](#design-trade-offs-and-limitations)) |
| Watchdog | Programmatic reconciliation handles execution and recovery. The LLM layer assesses progress from a bounded digest and records the last result and inference usage. |

## Design trade-offs and limitations

- **Context and memory.** The plugin builds each request from the current batch, ticket state, up to eight history stubs, and up to eight direct-delivery messages. Successful verdicts may update up to 12 durable notes with source trigger IDs. The inference service reports cache behavior.
- **Call budget.** Each evaluation or patrol permits at most 12 recalls and three calls with the same arguments. Recall text also has a combined cap. When the budget is exhausted the next request omits the tool list and asks for a verdict. Preparation, network calls, recall, and one format repair share the deadline.
- **Live UI refresh**: the conversation page and the sidebar receive state changes through the Paseo 0.16 plugin subscription `superagent.state_events`. Whenever the engine state changes (persisted records, an evaluation or patrol in progress, settings), the plugin pushes a revision after a 150 ms coalescing window, and the UI rereads `superagent.state` only when that revision differs from its cached snapshot. While the push is live, polling relaxes to a 30-second fallback (for fields that are not pushed, such as the program watchdog time); on an older app without the subscription API, or after the subscription closes (plugin reload, daemon restart), the UI goes back to polling every 3 seconds and subscribes again after 5 seconds. Worker session status comes from the daemon, and Router and patrol status come from the plugin snapshot.
- **Serial evaluation.** The engine processes one thread batch at a time and rechecks thread and trigger state before committing.
- **Failure backoff (two kinds)**: after 3 consecutive `unparsed` results (Router output cannot be parsed), the watchdog no longer requeues automatically, and a person must retry manually with "Re-evaluate" under "Tasks" in the right sidebar of the conversation, which prevents a runaway loop that burns tokens when the Router keeps degrading. Infrastructure errors (transient faults such as a provider not being ready or a directory being unavailable) do not count toward the circuit breaker; they are rechecked at the watchdog's pace for about 5 minutes (20 cycles), matching the article's "keep rechecking transient faults until they recover".
- **Permission waits**: a Worker's permission requests use Paseo's native permission flow, approved by a person in the app or with `/approve <code>`; the Ticket stays running during the wait and is not mistaken for complete.
- **External trigger sources**: Feishu/QQ are supported; GitHub/Slack polling sources are the next extension point (Paseo Hub triggers can also act as an upstream that delivers events to `superagent.dispatch`).
- **File preview**: the pill types are resolved by `superagent.stat_files`, which checks every path in a stretch of conversation in one call (at most 200, results cached for 1 minute). Previews are read by the daemon, read-only, through the `superagent.read_file` RPC for any absolute path (`~` expands to the daemon user's home directory), not limited to the workspace; a client that can reach the daemon can already make an agent run commands, so this adds no permission. Text is read up to 256 KB (only the beginning is shown beyond that), images up to 4 MB, directories list up to 500 entries; special files such as devices and pipes are not read; a file whose first 8000 bytes contain NUL is treated as binary and only its size is shown. Only links pointing to absolute paths in replies are recognized; relative paths and paths in inline code or code blocks are not. Files cannot be edited, and there is no jump to the host's file tab (plugin SDK 0.15 has no interface to open files). The host Modal's desktop card is fixed at a maximum width of 520 and the plugin cannot adjust it, so the desktop Web preview is drawn by the plugin with an RN Modal that imitates the host's dialog.
- **Verdict parsing.** The plugin validates the JSON and action constraints. It offers one format repair within the remaining time. If that fails, triggers stay pending and an `unparsed` decision is recorded.
- **Cancel semantics**: cancelling a Ticket archives the Worker agent, and the worktree workspace the Ticket owns exclusively is archived with it (soft delete, recoverable from History); shared persistent workspaces ("Default workspace" / profile workspaces) are kept and continue to serve later Tickets.
- **Delegation MCP channel**: `superagent_dispatch` is injected through the plugin's own MCP server (not through the daemon's plugin agent tools directory, so turning off "Paseo tools" in the host does not affect delegation). Cost: after a plugin reload the port and secret rotate, and calls using the old URL in an already open session fail with a connection error until the next session_open refreshes it; providers that do not support MCP servers are not injected by default (override with the "Providers to inject into" setting).
- **Orchestration tools.** The plugin evaluates read-only inference calls locally. Worker unsubscribe and handback, and ordinary Agent delegation, still use the local MCP bridge.
- **Misrouted direct delivery**: if a message delivered directly to the only subscribed Worker is unrelated to its ticket, the Worker uses `superagent_handback` to return it to the Router for re-routing (and may unsubscribe at the same time). The Router rules forbid steering the same message back to the Worker that handed it back, to prevent loops.
- **Dropped because of host (Paseo / plugin mechanism) limits**:
  - Stateless cloud compute + state in a database (the elastic form in §5.1): the plugin runs in a single daemon child process, so it can only do "persisted state + self-recovery after restart";
  - On-device lightweight daemon / BYOM / switching execution devices per task / catching up after an intermittently online device comes back (§5.2): the Paseo API the plugin gets corresponds only to the local daemon;
  - The watchdog timer runs in the engine process. The configured API performs only the model inference.
  - The watchdog rewriting prompts/trigger rules online: the plugin server can only read plugin settings, not write them, so changing rules is still done on the settings page;
  - Self-start after headless restart: the host does not give the plugin a Paseo handle at plugin startup, so the engine starts on the first hook/RPC (IM is already connected earlier and queues messages, so none are lost);
- **Dropped by requirement**: non-IM trigger sources such as GitHub/email/CI; only the existing five IM channels are supported;
- **Not done for now (high cost)**: merging across threads into one Router call (currently merged per thread, consistent with the official prototype); admission tiers at group/chat granularity (observe mode is currently switched per channel); parsing quote replies for DingTalk/WeCom (the channels do not return a usable message id).
