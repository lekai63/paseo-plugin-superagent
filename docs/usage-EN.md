# Usage

[← Back to README](../README.md) · [简体中文](usage.md)

The main screen is a chat page that works like talking to an agent in a Paseo project: the conversation is on the left, and the right sidebar holds everything that is not part of the conversation.

The Router reconstructs thread context from plugin state for every evaluation. IM inbound messages are bounded by the natural day in Beijing time, and channels, bot accounts and chats are isolated from each other; the platform's message root ID no longer splits a day's chat further. A cross-day quote of an old message keeps the quote summary, while the new message still goes into the day's thread. A new day does not interrupt old tasks; an old thread is closed automatically once it has no running tasks, pending triggers to evaluate, pending actions or cross-thread subscriptions, which archives its idle Workers. Cross-thread context is obtained through the recall and search tools.

Each evaluation includes saved constraints, append-only history stubs (kept up to 40, trimmed to 24 past the cap), up to eight direct-delivery messages, and current ticket state. Read-only recall retrieves details by ID. The Tasks sidebar shows latency, recall count, and the verdict.

1. **Conversation**: describe a task in the input box at the bottom to start a new conversation (a thread); the Router evaluates and either replies directly or dispatches a Worker. Sending more messages in the same conversation appends them to that thread. On desktop, the send key follows Paseo's global setting (Settings → General): by default Enter sends and Shift+Enter inserts a newline, and when set to Cmd/Ctrl+Enter a bare Enter inserts a newline; pressing Enter during IME composition does not send. Below the input box, a live hint shows where this message will go: new conversation, handed to the Router, or, when there are active subscriptions with an existing session, "Direct to Worker" (with several subscriptions, all of them get it directly); sending a message to a closed conversation reopens it. You can also type `/superagent Fix the CORS issue on the login page and add tests` in any agent session.
2. **Top tabs**: conversations in progress at the same time sit side by side as tabs; click to switch, and `+` starts a new conversation, which becomes a new tab once its first message is sent. The left of a tab shows its status: a spinning halo while the Router is evaluating or a Worker is running, a green dot when answered/complete, a red dot on error. Closing a tab (×) only collapses it; the conversation stays in "Conversations" in the right sidebar, and opening it from there makes it a tab again. When you close a conversation manually in the sidebar, its tab is closed as well (if it was the current conversation, you switch to the adjacent tab); conversations created by IM and agent delegation do not become tabs automatically. The tab list and the last viewed conversation are saved in the daemon state: after leaving the Superagent page or restarting the app, you go straight back to the last viewed conversation, and a new conversation is shown only when there is no open tab. Each tab keeps its own input draft. On first use, conversations started in the UI that are still in progress and active within the last 24 hours (at most 4) automatically become tabs.
3. **Message stream**: your messages (including IM messages from Feishu/QQ and so on, and agent delegations, with the source noted) appear as bubbles on the right, with a line below showing source, delivery status, time and copy; the Router's reply appears as Markdown text, with a footer below: copy · Router · time. Files linked by absolute path in a reply (and in an expanded Worker report), such as ``[`report.md`](/abs/report.md)``, `file://`, `:line` / `#L10-L20`, are listed as a row of file pills under the text (distinguished by the real type on disk: a folder is an amber tile with a right arrow, a file gets an icon by type and shows the line number, and a file that no longer exists is struck through). Opening one shows a preview (a dialog up to 1080 wide on desktop Web, the host overlay on phones and tablets): Markdown is rendered as Markdown, other text goes into a code block (with highlighting on Web), with a line number it first shows the excerpt around the reference, images are shown directly, and directories can be entered level by level; you can copy the path and re-read. The host's Markdown has no workspace context inside a plugin page, so a link in the body does nothing when clicked, which is why pills are used instead. Orchestration actions such as dispatch, steer, cancel, Worker report and evaluation failure are shown as compact expandable rows: a dispatch row follows the Ticket's live state and can open the Worker session directly, and a report row has a two-line preview that expands to the full original text. While the Router is evaluating or a Worker is running, a running indicator with elapsed time is shown at the bottom of the stream. It follows new messages automatically while you are at the bottom, and does not interrupt you while you scroll up.

   The layout borrows from the agent session redrawn by [better-paseo](https://github.com/RoundRedDot/better-paseo) (`shared/design.ts`, `client/theme-tokens.ts`): the content column width and the bubble and input font sizes follow the content width and body font size in Paseo's "Appearance" settings (bubble = body font size × 1.4 line height, same as the host); interface text uses a fixed scale (labels 13/18, meta 12/16, with extra line spacing for text that wraps); action rows are 26 tall on desktop and 28 on touch, finished rows fall back to a secondary color, running rows show a blue breathing dot, full contrast returns on hover or expand, and consecutive rows are only 4 apart; sidebar cards are raised cards with a hairline and a light shadow, failed/pending ones get a color wash, and buttons are hairline-outlined. All derived colors are mixed from the host theme. The Router's reply uses the host's built-in Markdown, whose line height (1.4×) is decided by Paseo.
4. **Right sidebar**: "Tasks" shows the Router's status and all Workers of the current conversation (all running Workers when no conversation is selected), with permission waits and session anomalies sorted first; you can open a session, cancel direct delivery (running) / mark complete (standby), retry, cancel a Ticket, and re-evaluate or close the conversation; cancel and close need a second click to confirm. "Conversations" lists conversations in progress and closed ones, and you can create one or open one as a tab; a conversation in progress can be closed directly: on desktop, hovering turns the updated-time spot in the row into an archive button (on touch it appears on the selected conversation), and clicking again to confirm closes it (and closes its tab too) without opening the conversation first; closed conversations are collapsed by default and expanded by default while you are viewing one of them. "Status" shows overview numbers, component configuration, watchdog patrols, and, when a reply was not delivered, "Undelivered IM replies" (the reply's opening identifies which one it is, and a failed one can be resent from where it broke). On wide screens the sidebar can be collapsed; on narrow screens and phones it opens as an overlay from a title bar button.
5. **Command Center**: "Superagent conversations" and "Superagent status" open the chat page and go to the corresponding sidebar tab.
6. **Viewing results**: the latest Router replies and Worker reports are persisted with the thread, so they remain visible in the conversation after the thread is closed and the Worker session reclaimed; old data is restored from the retained decisions/reports. New reports store the original text, while the Router's evaluation input is still truncated within the existing budget. The chat page reads the latest 120 triggers and decisions of a thread at a time; earlier records are not shown.
7. **Sidebar status**: to the left of Superagent is a fixed Network icon that follows the Paseo theme colors. To the right of the label, a "blue dot + number" shows the number of running Workers (it uses the same geometry as the count in better-paseo's "Tasks" row, aligned vertically between the two rows; the number scales with Paseo's interface font size), with the blue dot having a spinning halo; a "green dot + number" shows the number of Workers that completed this round and are on standby. When either count is 0 its dot and number are hidden, and when both are 0 or the status is unavailable, no counts are shown on the right. It updates live from the current Worker sessions; reclaimed sessions are not accumulated into the completed count, and queued tasks that have not started are not counted as running Workers. With the system's reduce-motion setting on, the halo stays still. When no Worker is running or on standby, a blue ring indicates Router evaluation and a red dot indicates evaluation errors on threads with pending triggers.

## Interface language

- The plugin UI follows Paseo's language setting (Settings → General → Language): with Simplified Chinese it shows Chinese, and every other language (including a non-Simplified-Chinese language resolved from "Follow system") shows English. Switching takes effect immediately without reloading the plugin, and input drafts and open tabs are unchanged.
- Text generated by the daemon (IM attachment and card descriptions, engine notices, WeChat QR-code status, file preview errors, and the names of workspaces the plugin creates: "Default workspace" / "Superagent background") is written in the language of the most recently connected client and is kept in the plugin state across restarts; it is English when no client has ever reported one. When several devices use different languages, the one that most recently opened Paseo wins. Trigger text and notices already written are not rewritten when the language is switched.
- After a language switch, the plugin finds an existing "Default workspace" / "Superagent background" by "current language name → the other language's name", so the same directory does not get a duplicate workspace.
- The built-in Router, Worker and watchdog prompts are always English; the language of the Router's replies depends on the message itself and your "Router rules". To fix a language, say so in "Router rules", for example "Always reply in Simplified Chinese".
