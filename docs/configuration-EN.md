# Settings

[← Back to README](../README-EN.md) · [简体中文](configuration.md)

After installation, a **Superagent** entry appears in the sidebar. Settings live in **Settings → Plugins → Superagent** (the chat page prompts you and jumps there in one click when nothing is configured; searching "Superagent settings" in the Command Center also opens it). All changes go into a draft first and take effect together when you click **Save**; invalid input is highlighted in red on its row:

| Setting | Description |
|---|---|
| Router evaluation timeout | `routerEvalTimeoutMin`, default 10 minutes, range 1–60. Preparation and verdict share one total budget, and preparation takes at most 1 minute; interrupt, cleanup, actions and sending also have their own wait limits. A late verdict is not executed; a Router that is only created successfully after the preparation timeout is archived automatically. Infrastructure errors are retried with a backoff that starts at 15 seconds and caps at 5 minutes; after 20 consecutive failures it pauses and notifies. After three consecutive parse failures it pauses and notifies. The counts and backoff time are persisted, and "Re-evaluate" resets them. When an action times out with an uncertain result, automatic resending pauses and a person is asked to confirm |
| Router idle recycle | `routerIdleTimeoutMin`, default 30 minutes, range 1–1440. Archives an idle Router and clears the reference, keeping the thread; the next evaluation rebuilds it automatically and restores the history context. Running Workers keep working. Recycling is postponed while there is an evaluation, a pending message/action/delivery, a Router a person is running manually, or a permission request |
| Conversation idle expiry | `threadIdleTimeoutMin`, default 1440 minutes (24 hours), range 5–43200. When there is no pending work, closes the thread automatically and reclaims leftover sessions. Valid inbound messages, Worker reports and real session activity renew it; patrols do not. A running task, a pending approval, cross-thread activity or an undelivered reply postpones closing. A new message after closing can reactivate a thread that is still retained; history follows the existing retention limits. The IM cross-day rule still applies |
| Worker standby recycle | `workerIdleTimeoutMin`, default 1440 minutes (24 hours), range 1–43200. A long-idle waiting ticket is completed and unsubscribed from all threads, its report is kept, and the Worker and its exclusive workspace are archived; shared workspaces are kept. The recycling intent is persisted, and the watchdog keeps cleaning up after a failure. It is postponed while there is a new message, a pending action, real running or an approval, and while the Worker still has shells or monitors running after its turn (the `backgroundWork` Paseo 0.16 reports); it is recycled once they stop. A wait on an approval/question longer than 24 hours triggers one reminder, and the request is kept for a person to handle |
| Working directory | An absolute path, the default base directory (**required**). With shared-directory isolation, the default Worker uses the ordinary persistent workspace "Default workspace" created for this directory (only one per directory; its id is recorded in the plugin state and reused across restarts; if it is archived it is found again by title + directory or recreated), and the Router and the watchdog use a background workspace on the same directory. With per-ticket worktree isolation it is the base repository from which each Ticket's worktree is cut. With `worktree` isolation it must be inside a git repository; otherwise both the chat page and the settings page warn about it, and a dispatch fails with the directory and the reason. The Router's evaluation prompt also states this directory and the isolation mode |
| Router provider/model | The settings page offers a dropdown from the daemon's provider snapshot (the model id is carried over as-is, including ACP-family ids with backslashes; if the list cannot be read or the chosen provider reports no models, it falls back to manual entry). Leave empty to automatically use the host's available default (claude → codex → opencode → any); if you enter something wrong, the Router evaluation reports the available ids |
| Thinking level (optional) | The Router, the default Worker and every named profile can each choose a thinking level independently (fields `routerThinkingOptionId` / `workerThinkingOptionId` / profile `thinkingOptionId`); the choices come from the `thinkingOptions` of the chosen provider/model (for example pi's low/medium/high/max). Choosing "Provider default" sends no `thinkingOptionId`, falling back to the provider's own default (for pi, `defaultThinkingLevel` in `~/.pi/agent/settings.json`); when the snapshot reports no list, you can type a level id by hand. The Router's level applies to newly created or rebuilt Router sessions (existing sessions are unaffected; switch them live with `paseo agent update <id> --thinking <level>`); a Worker's level is passed with the first task and applies only to newly created or retried Workers; a named profile left empty does not inherit the default Worker's level. It is validated against the snapshot before launch, and an invalid level reports the available IDs instead of silently falling back |
| Router custom rules | Entered directly in "Router rules" on the settings page, multi-line, at most 12000 characters; the config field is `routerInstructions`. Use it for reply language, dispatch preferences and report format; leave empty to use the default rules. Each thread reuses its Router session; when the rules, model or thinking configuration change, the session is rebuilt in a controlled way and its context restored, without relying on the provider reading `AGENTS.md`/`ROUTER.md`; it does not change the Workers' project rules. Custom rules supplement the built-in orchestration constraints, and the Router still only decides and outputs JSON actions. When a verdict fails to parse, the same session receives the specific syntax or validation error and gets one correction within the original evaluation timeout budget; if the correction still fails, the messages are kept for retry, and three consecutive failed rounds pause automatic retries |
| IM attachment inbox directory | `imInboxDir`, an absolute path on the daemon host; empty means `$PASEO_HOME/plugin-data/superagent/inbox`. Files received in chats are stored under `<directory>/<channel>/<Beijing-time date>/<message id>/`; a change takes effect for the next message immediately, without reconnecting channels. When the working directories of Worker profiles have their own filing rules, set this to a neutral directory outside them and let the Worker move files into the task directory according to those rules |
| Max characters per IM message | Default 600, range 100–4000 characters; the config field is still `imReplyMaxChars`. An over-long reply is split into several messages, preferring paragraph/line breaks, numbered `[1/N]` (the numbering counts toward the limit) and sent in order, with the full text preserved; ordinary emoji are split on grapheme boundaries. All parts are saved before sending, and progress is recorded after each part is confirmed. On failure it pauses, and you can resend from the failed part under **Status → Undelivered IM replies** in the chat page's right sidebar (this section lists only replies being sent or that failed to send, and disappears once everything has gone out). A restart resumes unfinished sends, and confirmed parts are not resent. If the remote side received a part but the receipt was lost, or a crash happened before persisting, that part may still be duplicated; the channels offer no unified exactly-once delivery guarantee |
| Worker provider/model | Same as above; the strongest model is recommended. When Worker profiles are configured it is the **default Worker**, and you can add a one-line purpose description |
| Worker mode (optional) | The default Worker and every named profile can choose a mode independently. For ordinary providers the choices come directly from the chosen provider's snapshot (including ACP dynamic modes) and match the mode IDs in Paseo's input box; choosing "Paseo default" sends no `modeId` and launches with Paseo's default behavior. When the provider is **pi**, the choices come from the [pi-permission-modes](https://pi.dev/packages/pi-permission-modes) extension on the daemon host (it reads `permission-mode/permission-mode.json` under `PI_CODING_AGENT_DIR` or `~/.pi/agent`, merged with the extension's stock modes), and the selected mode reaches new or retried Workers through the `PI_PERMISSION_MODE` environment variable (pi reports no modes, so a `modeId` would be rejected). When the extension is not installed only "Paseo default" is offered and Workers start on pi's own default mode. A named profile left empty also does not inherit the default Worker's mode. Switching provider clears the old mode, while changing the model within the same provider keeps the mode. The mode is passed with the first task, a change applies to newly created or retried Workers and does not modify running sessions; for ordinary providers an unsupported mode reports the available IDs before launch and does not silently fall back to the default mode |
| Worker profiles | Optional. Named profiles besides the default Worker (name + provider/model + purpose description + optional dedicated working directory), such as `code → codex/…` "Writing code, fixing bugs, running tests". In a dispatch the Router uses `"profile":"<name>"` to pick a profile for each task by purpose; when omitted or the name does not exist, the default Worker is used (in the latter case this is recorded in the decision). The Router can only use the models listed here, so trigger text cannot steer a Worker to an arbitrary provider. A profile's dedicated working directory must be an absolute path and may differ from the global working directory: with worktree isolation the profile cuts worktrees from its own directory; with shared-directory isolation that directory has a persistent workspace named after the profile (the same reuse mechanism as "Default workspace"). A Ticket records the chosen profile and the actual model: retry keeps the profile and launches with the model and directory currently set for that profile; if the profile has been deleted, the default Worker is used. With no profiles configured, behavior is exactly the same as a single Worker |
| Worker isolation | `worktree` (default, an independent branch workspace per Ticket) / `shared` (works directly in the base directory, no git needed. The default Worker uses the ordinary "Default workspace", and the Router and the watchdog use a separate background workspace. When the working directory root has `AGENTS.md`/`CLAUDE.md`, the Worker puts its output according to the filing rules in it and completes the required registration; without rules, each Ticket's output goes into a dedicated subdirectory `tasks/<Beijing-time date>-<title>-<id suffix>/`. Both the Router's and the Worker's prompts state this). Cancelling/closing a Ticket archives only the Worker session; the worktree workspace the Ticket owns exclusively is archived with it, and shared persistent workspaces are kept |
| Run Workers in the background | `workerBackground`, off by default. When on, new and retried Workers are created as Paseo 0.16 background agents: they stay out of Paseo's tabs, default lists, the Router's Subagents track and finished/error notifications, and you still open them per Ticket from the plugin's conversation page and can take over. With per-ticket worktree isolation, the workspace the Ticket owns is created as a background workspace too; the shared "Default workspace" and profile workspaces stay ordinary workspaces. Worker permission requests and questions are still relayed through the Router/IM. When off, Workers are explicitly created as ordinary agents, so they never inherit a background flag from their parent session. Workers already running are not affected |
| Worker timeout / Failure retries / Batch window / Max characters per message | Engine tuning (in the "Execution" group of the settings page; out-of-range values are flagged in place) |
| Speculative execution | In the "Proactive & patrol" group, off by default. When on, the Router rules include a speculative-execution description, and the Router can dispatch `speculative` Workers following the proactive policy you write in "Router rules" (for example "when someone reports a problem in the group, quietly reproduce it and try a simple fix"); at most 2 at a time, and extra speculative dispatches are dropped directly and recorded in the decision |
| LLM watchdog | In the "Proactive & patrol" group, off by default. When the watchdog model is empty it uses the Router's model; the patrol interval is 5–240 minutes (default 30). When there is no unfinished task and no anomaly, the patrol is skipped and the model is not called (a released Router session that will be rebuilt on the next evaluation is not an anomaly; for standby tasks that were delivered and are waiting for follow-up messages, an idle Worker with no new activity since the last patrol is not one either; failed IM replies count as an anomaly only within two patrol intervals, after which they are left to the "Status" page for resending); while a maintainer is talking to the watchdog session, this patrol yields |
| Inject the delegation tool into agents | When on, the `superagent_dispatch` tool is injected into the sessions of all ordinary agents. It goes through the plugin's **own local MCP server** (`127.0.0.1`, random port + random secret path) and is not affected by the host's "Paseo tools" (`mcp.injectIntoAgents`) switch. The same endpoint also delivers tools by role to the orchestrator's own sessions: the Router gets `superagent_list`/`superagent_read`/`superagent_search` (read-only recall and search), and the Worker gets `superagent_unsubscribe`/`superagent_handback` (session control); this part is not controlled by this switch. Role tools are **injected through session_open at every session start**; they cannot be written into the agent's saved config: a same-named mcpServer conflicts with the plugin's injection and is rejected by the daemon, and a server referenced by `toolPolicy` pre-authorization must appear in the same request, so neither route works |
| Providers to inject into | The provider families allowed to receive the above MCP injection, comma-separated (such as `codex,claude`); empty = claude,codex,opencode,omp,copilot. Injection into providers that do not support MCP servers (such as the ACP family) would make the session fail to start, so they are excluded by default; the pi family is the exception: it uses the env + pi extension channel (see [pi integration](pi-EN.md)), and entering `pi` here injects the delegation tool into ordinary pi sessions. Role-tool injection for the Router/Worker is gated by family in the same way, "default list ∪ this list" (when a provider carries a model qualifier, the family before `/` is used; for plugin-type providers such as zcode-acp, the daemon declares MCP support uniformly, so to inject into one, configure it here) |
