# Settings

[← Back to README](../README.md) · [简体中文](configuration.md)

After installation, a **Superagent** entry appears in the sidebar. Settings live in **Settings → Plugins → Superagent** (the chat page prompts you and jumps there in one click when nothing is configured; searching "Superagent settings" in the Command Center also opens it). The settings are split into five tabs — **Basics / Models / Rules / Execution / IM triggers**. All changes go into one shared draft that survives tab switches, and take effect together when you click **Save**; invalid input is highlighted in red on its row:

| Setting | Description |
|---|---|
| Router evaluation timeout | `routerEvalTimeoutMin`, default 10 minutes, range 1–60. Preparation, inference, recall, and one format repair share a deadline, with up to one minute for preparation. Timeout aborts the request and discards late verdicts. API errors back off from 15 seconds to 5 minutes for up to 20 attempts. Three consecutive parse failures pause automatic evaluation. |
| Conversation idle expiry | `threadIdleTimeoutMin`, default 1440 minutes (24 hours), range 5–43200. When there is no pending work, closes the thread automatically and reclaims leftover sessions. Valid inbound messages, Worker reports and real session activity renew it; patrols do not. A running task, a pending approval, cross-thread activity or an undelivered reply postpones closing. A new message after closing can reactivate a thread that is still retained; history follows the existing retention limits. The IM cross-day rule still applies |
| Worker standby recycle | `workerIdleTimeoutMin`, default 1440 minutes (24 hours), range 1–43200. A long-idle waiting ticket is completed and unsubscribed from all threads, its report is kept, and the Worker and its exclusive workspace are archived; shared workspaces are kept. The recycling intent is persisted, and the watchdog keeps cleaning up after a failure. It is postponed while there is a new message, a pending action, real running or an approval, and while the Worker still has shells or monitors running after its turn (the `backgroundWork` Paseo 0.16 reports); it is recycled once they stop. A wait on an approval/question longer than 24 hours triggers one reminder, and the request is kept for a person to handle |
| Working directory | Absolute path on the daemon host. Set it to launch the default Worker. Shared isolation reuses a workspace by directory. Worktree isolation requires a Git repository. |
| Inference API base URL and Router model | `inferenceBaseUrl` and `routerModel`. Use a Chat Completions API with function calling. Include the API version path, for example `https://inference.example/v1`. The plugin appends `/chat/completions`. For Bearer authentication, enter the key in the **Inference API key** field (`inferenceApiKey`). Use HTTPS for remote endpoints. HTTP is supported for loopback IP addresses such as `127.0.0.1` and `[::1]`. |
| Thinking level (optional) | The default Worker and each named profile can set a thinking level offered by the Paseo provider. |
| Router custom rules | `routerInstructions`, up to 12,000 characters, with multiple lines allowed. The plugin sends them with the system message on every evaluation. |
| IM attachment inbox directory | `imInboxDir`, an absolute path on the daemon host; empty means `$PASEO_HOME/plugin-data/superagent/inbox`. Files received in chats are stored under `<directory>/<channel>/<Beijing-time date>/<message id>/`; a change takes effect for the next message immediately, without reconnecting channels. When the working directories of Worker profiles have their own filing rules, set this to a neutral directory outside them and let the Worker move files into the task directory according to those rules |
| Max characters per IM message | Default 600, range 100–4000 characters; the config field is still `imReplyMaxChars`. An over-long reply is split into several messages, preferring paragraph/line breaks, numbered `[1/N]` (the numbering counts toward the limit) and sent in order, with the full text preserved; ordinary emoji are split on grapheme boundaries. All parts are saved before sending, and progress is recorded after each part is confirmed. On failure it pauses, and you can resend from the failed part under **Status → Undelivered IM replies** in the chat page's right sidebar (this section lists only replies being sent or that failed to send, and disappears once everything has gone out). A restart resumes unfinished sends, and confirmed parts are not resent. If the remote side received a part but the receipt was lost, or a crash happened before persisting, that part may still be duplicated; the channels offer no unified exactly-once delivery guarantee |
| Worker provider/model | Same as above; the strongest model is recommended. When Worker profiles are configured it is the **default Worker**, and you can add a one-line purpose description |
| Worker mode (optional) | The default Worker and every named profile can choose a mode independently. For ordinary providers the choices come directly from the chosen provider's snapshot (including ACP dynamic modes) and match the mode IDs in Paseo's input box; choosing "Paseo default" sends no `modeId` and launches with Paseo's default behavior. When the provider is **pi**, the choices come from the [pi-permission-modes](https://pi.dev/packages/pi-permission-modes) extension on the daemon host (it reads `permission-mode/permission-mode.json` under `PI_CODING_AGENT_DIR` or `~/.pi/agent`, merged with the extension's stock modes), and the selected mode reaches new or retried Workers through the `PI_PERMISSION_MODE` environment variable (pi reports no modes, so a `modeId` would be rejected). When the extension is not installed only "Paseo default" is offered and Workers start on pi's own default mode. A named profile left empty also does not inherit the default Worker's mode. Switching provider clears the old mode, while changing the model within the same provider keeps the mode. The mode is passed with the first task, a change applies to newly created or retried Workers and does not modify running sessions; for ordinary providers an unsupported mode reports the available IDs before launch and does not silently fall back to the default mode |
| Worker profiles | Optional. Named profiles besides the default Worker (name + provider/model + purpose description + optional dedicated working directory), such as `code → codex/…` "Writing code, fixing bugs, running tests". In a dispatch the Router uses `"profile":"<name>"` to pick a profile for each task by purpose; when omitted or the name does not exist, the default Worker is used (in the latter case this is recorded in the decision). The Router can only use the models listed here, so trigger text cannot steer a Worker to an arbitrary provider. A profile's dedicated working directory must be an absolute path and may differ from the global working directory: with worktree isolation the profile cuts worktrees from its own directory; with shared-directory isolation that directory has a persistent workspace named after the profile (the same reuse mechanism as "Default workspace"). A Ticket records the chosen profile and the actual model: retry keeps the profile and launches with the model and directory currently set for that profile; if the profile has been deleted, the default Worker is used. With no profiles configured, behavior is exactly the same as a single Worker |
| Worker isolation | `worktree` creates an isolated workspace per ticket by default. `shared` reuses a persistent workspace by base directory or profile. |
| Run Workers in the background | `workerBackground`, off by default. New and retried Workers stay out of Paseo's default lists and can still be opened from Superagent. |
| Worker timeout / Failure retries / Batch window / Max characters per message | Engine tuning (in the "Execution" group of the settings page; out-of-range values are flagged in place) |
| Speculative execution | In the "Proactive & patrol" group, off by default. When on, the Router rules include a speculative-execution description, and the Router can dispatch `speculative` Workers following the proactive policy you write in "Router rules" (for example "when someone reports a problem in the group, quietly reproduce it and try a simple fix"); at most 2 at a time, and extra speculative dispatches are dropped directly and recorded in the decision |
| LLM watchdog | Off by default under Proactive & patrol. A blank `watchdogModel` uses the Router model. Patrols run every 5–240 minutes, default 30, and skip inference when nothing requires attention. |
| Inject the delegation tool into agents | When on, the `superagent_dispatch` tool is injected into the sessions of all ordinary agents. It goes through the plugin's **own local MCP server** (`127.0.0.1`, random port + random secret path) and is not affected by the host's "Paseo tools" (`mcp.injectIntoAgents`) switch. The same endpoint also delivers session-control tools to Worker sessions: `superagent_unsubscribe`/`superagent_handback`; this part is not controlled by this switch. Role tools are **injected through session_open at every session start**; they cannot be written into the agent's saved config: a same-named mcpServer conflicts with the plugin's injection and is rejected by the daemon, and a server referenced by `toolPolicy` pre-authorization must appear in the same request, so neither route works. The Router and watchdog no longer use this channel: their read-only recall runs inside the inference loop |
| Providers to inject into | The provider families allowed to receive the above MCP injection, comma-separated (such as `codex,claude`); empty = claude,codex,opencode,omp,copilot. Injection into providers that do not support MCP servers (such as the ACP family) would make the session fail to start, so they are excluded by default; entering `pi` here injects the delegation tool into ordinary pi sessions (tools are exposed through pi's codemode channel, see [Pi integration](pi-EN.md)). Role-tool injection for the Router/Worker is gated by family in the same way, "default list ∪ this list" (when a provider carries a model qualifier, the family before `/` is used; for plugin-type providers such as zcode-acp, the daemon declares MCP support uniformly, so to inject into one, configure it here) |
